## Representation

> 1. your representation (element type and base), and why

`BigInt` is represented by a vector of decimal digits plus a sign bit. This is wasteful memory-wise and slower than base 2, but makes it extremely easy to display as it is already in base 10.

My initial attempt was to use a vector of `size_t`, storing numbers using two's compliment. This was good in that it was maximally space-efficient and both addition and subtraction were speedy, but I ended up scrapping it since it would require me to implement binary division in order to convert the base 2 to base 10 for `toString()`, `operator[]`, and `digitCount()`, which I do not have time or energy for this week as I am studying for midterms. There were also other problems with this approach, namely two's compliment leverages overflow for subtraction to work, and so an extra leading "sign extension" digit was required to maintain this property, which may as well have been a sign bit. It was kind of a mess.

I also experimented with storing the unsigned magnitude as a vector of `size_t` with a separate sign boolean, which was more reliable, but ultimately it also required division in order to display in base 10 so I had to either implement division or give up and use base 10 storage. I begrudgingly chose the latter.

> 4. your estimate for another representation


I would estimate that proper base 2 representation would be significantly more space-efficient. Using a whole byte to represent a single decimal digit wastes 96% of the byte as it only ever uses 10 of the 256 possible values. Another way of thinking about this is that since a byte is the minimum addressable unit, using the whole byte is like upgrading from base-10 to base-256. I wouldn't just use a vector of bytes though; I would use a vector of register-width unsigned integers (`size_t`) to better leverage the hardware in order to speed up arithmetic operations significantly.

Since `factorial<BigInt>(10000)` can be represented by 35660 decimal digits, I would expect it to fit in 1393 bytes, a *significant* decrease in size.
